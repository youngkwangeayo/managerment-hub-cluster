멀티 클러스터 아키텍처의 꽃이자 가장 중요한 보안 연결 고리인 '타겟 클러스터 자격 증명(Token) 추출' 단계입니다.

EKS, GKE, NKS 등 벤더사가 달라도 쿠버네티스 표준 API를 사용하기 때문에 추출하는 원리와 명령어는 100% 동일합니다. 이것이 쿠버네티스의 가장 큰 장점(Cloud-Agnostic)이죠.

타겟 클러스터(A 또는 B) 터미널에 접속하신 상태에서 아래 4단계를 순서대로 진행하시면 됩니다.

🚀 타겟 클러스터(A, B) Kubeconfig Token 추출 가이드
이 작업은 Hub가 배포를 수행할 타겟 클러스터(A, B)에서 각각 수행해야 합니다.

Step 1: Argo CD 전용 ServiceAccount 및 권한(RBAC) 생성
타겟 클러스터에 접속하여 Hub의 Argo CD가 사용할 계정과 권한을 만들어 줍니다. Argo CD는 K8s의 모든 리소스(Namespace, CRD 등)를 생성하고 지워야 하므로 통상적으로 cluster-admin 권한을 부여합니다.

```Bash
# 1. 네임스페이스 생성 (선택 사항이지만 관리를 위해 추천)
kubectl create namespace argocd-manager

# 2. ServiceAccount 생성
kubectl create serviceaccount argocd-manager -n argocd-manager

# 3. ClusterRoleBinding 생성 (최고 관리자 권한 부여)
kubectl create clusterrolebinding argocd-manager-role-binding \
  --clusterrole=cluster-admin \
  --serviceaccount=argocd-manager:argocd-manager
```
Step 2: 장기(Long-lived) 토큰 Secret 생성 (🌟 K8s 1.24+ 필수)
쿠버네티스 1.24 버전부터는 ServiceAccount를 만들어도 토큰(Secret)이 자동으로 생성되지 않습니다. 따라서 만료되지 않는 장기 토큰을 보관할 Secret을 직접 만들어주어야 합니다.

아래 내용으로 argocd-manager-secret.yaml 파일을 만들고 적용합니다.

YAML
apiVersion: v1
kind: Secret
metadata:
  name: argocd-manager-token
  namespace: argocd-manager
  annotations:
    kubernetes.io/service-account.name: "argocd-manager"
type: kubernetes.io/service-account-token
```Bash
# 시크릿 생성 적용
kubectl apply -f argocd-manager-secret.yaml
```
Step 3: Bearer Token 추출
이제 생성된 Secret에서 Argo CD values.yaml에 집어넣을 토큰 값을 뽑아냅니다.

```Bash
# 토큰 값을 디코딩하여 출력
kubectl -n argocd-manager get secret argocd-manager-token -o jsonpath='{.data.token}' | base64 -d
```
출력 결과 (예시): eyJhbGciOiJSUzI1NiIsImtpZCI... (엄청나게 긴 문자열)
👉 이 값을 복사해서 허브의 values.yaml 안의 bearerToken 항목에 붙여넣습니다.

Step 4: CA Certificate (caData) 추출
안전한 HTTPS 통신을 위해 타겟 클러스터의 인증서 정보(caData)도 필요합니다.

```Bash
# ca.crt 값을 그대로 (Base64 인코딩된 상태로) 출력
kubectl -n argocd-manager get secret argocd-manager-token -o jsonpath='{.data.ca\.crt}'
```
출력 결과 (예시): LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0t...
👉 이 값을 복사해서 허브의 values.yaml 안의 tlsClientConfig.caData 항목에 붙여넣습니다.

💡 벤더사별(EKS, GKE, NKS) 차이점 및 실무 팁
위의 1~4단계 명령어는 EKS, GKE, NKS 어디서든 토씨 하나 틀리지 않고 똑같이 작동합니다. 이것이 바로 '토큰 기반 인증(Bearer Token Authentication)'의 강력함입니다.

하지만 벤더사 환경에 따라 네트워크 관점에서 딱 한 가지 확인해야 할 점이 있습니다.

API 서버 엔드포인트 접근성: Hub 클러스터(A)가 타겟 클러스터(GKE, NKS 등)의 API 서버 주소(https://...)로 통신을 보낼 수 있어야 합니다.
만약 타겟 클러스터의 API 서버가 퍼블릭으로 열려 있다면 방화벽(Authorized Networks)에 Hub 클러스터의 NAT Gateway 공인 IP를 화이트리스트로 추가해 주어야 통신 에러(Timeout)가 발생하지 않습니다.

EKS to EKS 환경의 또 다른 방법 (참고용):
현재 Hub, A, B가 모두 EKS 환경이라면, 토큰을 발급받는 대신 AWS의 IAM Role(IRSA)과 aws-auth ConfigMap을 엮어서 인증하는 방식도 가능합니다. 하지만 나중에 NKS나 GCP 등 멀티 클라우드로 확장할 계획이 확고하시다면, 지금 알려드린 '표전 토큰 추출 방식'으로 통일해서 세팅하는 것이 아키텍처의 일관성 유지에 훨씬 유리합니다.

타겟 클러스터에서 값을 무사히 추출하셨나요? 추출한 bearerToken, caData, 그리고 타겟 클러스터의 API 서버 URL을 hub-setup/values.yaml에 넣으시면 모든 물리적 연동 준비가 끝납니다!
